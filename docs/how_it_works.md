# How LedgerLens works — start here

**This document assumes nothing.** No data-warehouse background, no analytics vocabulary,
no familiarity with the codebase. If you have just cloned this repo, read this before
anything else.

Every term is explained the first time it appears. By the end you will be able to read the
[README](../README.md) and [contracts_decisions.md](contracts_decisions.md), both of which
assume the vocabulary this page teaches.

---

## 1. What problem this solves

Imagine you run a subscription software company. Every morning you check a dashboard. One
day it says:

> **Renewal revenue is down 8%.**

The dashboard tells you *what* happened. It cannot tell you **why**. So an analyst spends
three days digging through Slack, Jira, deploy logs and support tickets.

The expensive failure is not the three days. It is **acting on the wrong why**. If revenue
fell because your payment code broke, but you conclude "marketing cut the budget," then
you restore the marketing budget and the bleeding continues.

LedgerLens automates the *why*. It is a detective, not a dashboard.

## 2. The eight words you need

| Word | What it means |
|---|---|
| **KPI** | "Key Performance Indicator" — a number a business watches. That is the whole definition. |
| **Dimension** | A way of slicing the business: by region, by customer size, and so on. |
| **Cohort** (or **slice**) | One specific combination of dimension values. |
| **Fact table** | The big table of numbers, one row per day per slice. |
| **Baseline** | What you *expected* the number to be. |
| **Anomaly** | A number meaningfully different from its baseline. |
| **Change event** | Something the company deliberately did — a code deploy, a price change. |
| **Blast radius** | Which slices a change event could possibly have affected. |

### The two KPIs here

- **`mrr_renewals`** — money from existing customers renewing, per day. *MRR* is
  "Monthly Recurring Revenue," standard subscription-business jargon.
- **`new_logo_bookings`** — money from brand-new customers. *"New logo"* means a new
  company, because you would add their logo to your customers page.

### The four dimensions

| Dimension | Values | What it actually is |
|---|---|---|
| `region` | DACH, UK, FR, US, APAC, Nordics | Where the customer is. **DACH** = Germany, Austria, Switzerland. |
| `segment` | Enterprise, Mid, SMB | How big the customer is. SMB = small/medium business. |
| `payment_rail` | sepa, card, invoice | **How the money physically moves.** SEPA is the European bank-transfer system. |
| `product` | A, B, C | Which product they bought. |

So a **cohort** is something like `{region: DACH, segment: Enterprise, payment_rail: sepa}`
— German-speaking large companies paying by European bank transfer.

A row of the **fact table** (`fact_metric`) reads:

> on 2026-08-03, for `mrr_renewals`, in DACH / Enterprise / sepa / product A → **$12,431**

About 550 days × ~150 slices × 2 KPIs.

### The omission rule — read this twice

> **A dimension you do not mention means *all* of them.**

`{region: DACH}` does not mean "DACH only, ignore everything else." It means **all of
DACH** — every segment, every payment rail, every product. The unmentioned dimensions are
*unconstrained*.

This is not intuitive, and the entire scoring system turns on it. Come back to this in §6.

## 3. The story the demo tells

The data is invented — generated by `ledgerlens/gen_data.py`. That is deliberate and it is
the point: **because the project plants the answer, it can prove the tool found the right
one** instead of merely looking convincing.

Here is what was planted.

**The real cause.** On **Aug 3, 2026**, an engineer deployed new code to the SEPA payment
connector (`deploy_sepa_v214`). It broke. Renewals for **DACH × Enterprise × sepa**
collapsed to **15% of normal**. Damage: **−$410,000**.

**The decoy.** On **Aug 1** — two days *earlier* — marketing cut the DACH advertising
budget (`campaign_dach_cut`). This is a trap, and a good one:

- it happened *before* the drop, so the timing looks guilty
- it is in DACH, so the location looks guilty
- it is **completely innocent** of this particular problem

A human looking at *"DACH revenue is down, and we cut DACH marketing"* would very
reasonably blame marketing. **They would be wrong**, and the fix they chose would not work.

**The second decoy.** A US price change — discarded instantly, because US and DACH have no
overlap at all.

Everything below exists to reach the right verdict *and show its work*.

## 4. The three streams of data

```
   METRICS               CHANGE LEDGER              SYMPTOMS
   the numbers           things we did              customer pain
   fact_metric           change_event               ticket
        │                      │                        │
        └──────────┬───────────┴────────────────────────┘
                   ▼
              the pipeline
```

**Metrics** — the daily revenue numbers.

**The change ledger** — the central idea. Every deliberate change becomes a row: deploys
(from GitHub), feature flags (from LaunchDarkly), campaigns (from a calendar), price
changes (from a pricing database). Four different systems, one table.

**Symptoms** — support tickets. Used only as *corroborating* evidence and **deliberately
never scored**. If 42 people complain about SEPA failures that week, that is supporting
testimony, not proof.

The README's [Pipeline section](../README.md#pipeline) has the full diagram with the
engine stages drawn in.

## 5. The six stages

This is `pipeline.run()` in [`ledgerlens/pipeline.py`](../ledgerlens/pipeline.py). It is a
straight line — no AI agent, no magic, and nothing that can wander.

### Stage 1 — DETECT: "did anything break, and when?"

Walk backwards through the daily totals. For each day ask two questions:

1. Is this day **statistically weird**? (unusual compared to normal wobble)
2. Is the drop **big enough to matter**? (at least 3%)

Both must be true, on **two consecutive days**. That combination is the **onset**.
Answer: **Aug 3**.

Requiring both is what makes it reliable. August is a naturally slow month — a −1.2%
seasonal dip. On statistics alone, that dip would occasionally trip the alarm by chance.
It can never reach −3%, so demanding practical significance too makes the result
deterministic rather than a coin flip.

### Stage 2 — DRILL: "where exactly?"

The best part. It starts at the top — *"all renewals are down 8%"* — then asks: **which
dimension explains this best?**

```
all renewals            −8.2%
└── region: DACH        ← DACH explains most of it
    └── segment: Enterprise
        └── payment_rail: sepa      ← stop here
```

It stops at **DACH × Enterprise × sepa**. That is the **focal cohort**: the narrowest
slice that actually accounts for the damage.

Crucially it only descends into branches that are *themselves* anomalous. It never tests
all ~150 combinations — just the guilty path. That is why it is fast and why the result is
explainable.

### Stage 3 — SYMPTOMS

Pull clusters of support tickets from that time window, for corroboration.

### Stage 4 — CANDIDATES: "what could have done this?"

Two filters. Both trivial, both deterministic.

**Filter 1 — time.** Did it happen in the 21 days before the drop? An event *after* the
drop cannot have caused it.

**Filter 2 — overlap.** Does the change's **blast radius** intersect the focal cohort?

Now the omission rule from §2 does real work:

| Change | Declared blast radius | Why |
|---|---|---|
| SEPA deploy | `{region: DACH, payment_rail: sepa}` | shipped to DACH, touches the SEPA code path |
| Marketing cut | `{region: DACH}` | a campaign targets a *place*, not a payment method |
| US price change | `{region: US}` | — |

US ∩ DACH = **empty**. The price change is gone before it is ever scored.

> **Why this is the strong idea:** companies *already record this*. A deploy knows which
> regions it rolled out to. A feature flag knows its targeting rules. A campaign knows its
> geography. So "is this change relevant to this anomaly?" becomes a **set intersection** —
> instant, deterministic, explainable in one sentence — instead of AI inference over prose.
> The blast radius is never guessed from text. It is read from metadata the source system
> already has.

### Stage 5 — SCORE AND TEST

### Stage 6 — NARRATE

Turn the result into the human-readable diagnosis card.

## 6. Scoring: T, C, D, N, P

Each surviving candidate gets five sub-scores, combined using fixed weights. **Not one of
them is an AI opinion** — every one is a database query you can re-run yourself.

| | Name | The question it asks | Weight |
|---|---|---|---|
| **T** | Temporal | Did it happen shortly before the break? | 0.25 |
| **C** | Cohort match | How well does its blast radius match the broken slice? | 0.30 |
| **D** | Dose–response | More exposure → more damage? | 0.15 |
| **N** | Negative controls | Did it survive attempts to *disprove* it? | 0.25 |
| **P** | Prior | Have analysts confirmed this kind of cause before? | 0.05 |

The weights are printed on screen rather than hidden inside the code. A weighting is a
product decision someone should be able to argue with — not a secret setting.

### Watch C do the work

**C** measures overlap between the blast radius and the focal cohort — the shared slices
divided by the total slices involved.

| Candidate | Blast radius covers | Focal cohort is | C |
|---|---|---|---|
| SEPA deploy | 9 slices (DACH × 3 segments × sepa × 3 products) | 3 of them | **0.333** |
| Marketing cut | 21 slices (all of DACH) | 3 of them | **0.143** |

The marketing cut is punished for being **vague**. It did not name a payment rail, so by
the omission rule its radius swelled to all of DACH — and a wide claim matches a narrow
problem badly.

**The system prefers specific explanations over sweeping ones.** That falls directly out
of the omission rule, which is why §2 asked you to read it twice.

## 7. Negative controls — the best idea in the project

Slow down here. This is what separates the tool from a correlation engine.

Most analysis asks: *"what evidence supports my theory?"* That is how you fool yourself —
you will always find something.

LedgerLens asks the opposite:

> **"If this theory were true, what ELSE would have to be true? Let us go check."**

Then it actually runs those checks. This is **falsification, mechanized**.

### How the decoy dies

The marketing theory says: *a DACH-wide budget cut caused this.*

If that were true, then **DACH Mid and SMB customers should have dropped too**. A budget
cut cannot somehow spare smaller customers — there is no mechanism by which it could.

Go and look. They came in at **−1.3%**. Flat. Completely normal.

The prediction **failed**. So the theory is dead: **N drops to 0.00 and the hypothesis is
rejected outright** — not merely ranked lower. On screen it appears struck through, in a
red banner naming the exact check that killed it.

### Why the deploy survives

The deploy theory says: *only the SEPA code path broke.* That makes checkable predictions:

- DACH customers paying by **card** should be fine → they were
- **Other regions** on SEPA should be fine → they were
- and two more

All four held. **N = 1.00.**

### The verdict

| | T | C | D | N | **total** | |
|---|---|---|---|---|---|---|
| `deploy_sepa_v214` | 1.00 | 0.333 | 0.50 | 1.00 | **0.700** | 4/4 controls pass |
| `campaign_dach_cut` | 0.72 | 0.143 | 0.50 | **0.00** | 0.322 | **REJECTED** |

Note the decoy's **T = 0.72** — its timing genuinely was more suspicious than most. It
still loses, because timing is not evidence when the mechanism is testable.

### The honest coda

The marketing cut *did* cause something real: DACH `new_logo_bookings` fell **−31%**,
exactly what a budget cut is supposed to do. It is the **wrong metric for this anomaly**,
not a harmless event — and the card raises it separately rather than pretending nothing
happened.

## 8. "Every number traces to a query"

You will see this phrase everywhere. Here is what it means.

Exactly one function may talk to the database: **`Store.q()`**
([store.py](../ledgerlens/store.py)). When you use it, it:

1. runs your SQL
2. makes a fingerprint of it — `q_87fa09d8c9` — called a **query_id**
3. logs the SQL, the inputs, and a preview of the result
4. hands back the data **and** the id

So every number on screen carries a receipt. Click any figure and you see the exact SQL
that produced it. There is a test that walks a finished diagnosis card, collects every id,
re-runs each one, and checks the answer still matches.

> **Why this matters more than it sounds.** The standard objection to any AI analytics
> tool is *"how do I know it didn't just make that up?"* Here the answer is **structural,
> not a promise**: a number without a source is impossible to produce. The architecture
> forbids it.

## 9. Where `contracts.py` fits

Everything above is the **detective**. `contracts.py` is something different, and missing
this distinction is what makes [contracts_decisions.md](contracts_decisions.md)
disorienting on a first read.

**`contracts.py` is the rulebook. It does not find causes.**

Think about what happens when Finance and Sales both say "revenue" and quietly mean
different things. Every meeting becomes an argument about whose number is right. The fix is
to write the definition down and have everyone agree to it.

That written agreement is a **KPI semantic contract**:

| Part | Plain meaning |
|---|---|
| `definition` | one sentence a human can read |
| `calculation_sql` | the exact SQL — no ambiguity possible |
| `unit`, `owner` | "$/day", "revenue operations" — and who to ask |
| `drivers` | things known to move this number |
| `thresholds` | how weird it must get before we raise an alarm |
| `lineage` | where the data came from |
| `access` | which roles may see which slices |

### Why it is code and not a wiki page

Most companies write this as a wiki page. A wiki page is true the day it is written and
quietly false six months later — **and nothing ever notices**.

Here it is Python that the program actually reads. The detector reads its `thresholds`.
The screen renders its `calculation_sql`. So when the document and the code disagree,
**a test fails**.

That is the whole argument: **a wiki page cannot fail a test.**

### The freshness panel

One thing the contract does that is worth seeing. It *declares* how often each data source
updates. A separate function goes and *measures* what is actually there:

| source | promises | actually is |
|---|---|---|
| billing_db | daily batch, 02:00 UTC | **0 days old** |
| github | instant webhook | 12 days old |
| calendar | weekly export | 15 days old |

The `github` row is the honest one. It promises *seconds* and reads *12 days* — but that
is **not a broken pipeline**. It means nobody deployed anything for 12 days. For an event
feed, "lag" measures how *rare* events are, not how *stale* the data is. Treating those as
the same thing would be the panel lying to you.

## 10. Jargon decoder

For terms you will hit in the other documents.

| Term | Plain meaning | Here |
|---|---|---|
| **grain** | "what does one row of this table represent?" | `fact_metric`: one row per day per region per segment per rail per product |
| **lineage** | the chain the data travelled | `github` → `data/events_deploys.json` → `change_event` |
| **refresh cadence** | how often a source *claims* to update | "daily batch, 02:00 UTC" |
| **freshness / lag** | how stale the newest row *actually is* | cadence is a **promise**, freshness is the **measurement** |
| **as_of** | the date the demo pretends "today" is | 2026-08-17 — everything is measured relative to it, not the real clock |
| **warmup** | how much history you need before "normal" means anything | 120 days; below that the system **refuses to guess** and says so |
| **MAD** | "median absolute deviation" — how much a number normally wobbles | see below |
| **robust z** | how many normal-wobbles from expected a value sits | the focal cohort is at z ≈ −40. Not noise. |
| **fail-open / fail-closed** | when a rule does not match, allow or deny? | a locked door is fail-closed; a door that opens when power dies is fail-open |
| **dimension-level security** | governs which *cuts* you may see | "you cannot break revenue out by payment rail" — this is what we do |
| **row-level security** | governs which *records* you may see | "you cannot see European customers at all" — deliberately not done |
| **Pydantic / validator** | a library that checks data shapes; a rule like "region must be one of these six" | type `"regoin"` and the program **refuses to start** |
| **drift** | documentation and code slowly disagreeing | the enemy the contract exists to prevent |
| **SCD-2** | keep old rows with date ranges instead of overwriting | how a price change is detected: compare consecutive versions |

### Why MAD and not the usual standard deviation

Standard deviation measures spread using averages — and averages get **dragged toward
extreme values**. When you are hunting an outlier, that outlier inflates your definition of
"normal wobble" and **hides itself**.

MAD uses medians, which ignore extremes. It is the difference between *average* income
(one billionaire skews it) and *median* income (does not).
